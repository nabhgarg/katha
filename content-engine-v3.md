# Katha Content Engine v3 — Production Specification

**Status:** Draft for Nabh review before implementation.
**Voice optimization:** Explicitly deferred. v3 ships structure + content-quality wins only.
**Migration target:** Single-file `index.html` (current Katha codebase).

This is the working middle-ground between (a) the current pipeline (Bible → Arc → Scenes A/B → Cover → save once at end) and (b) the v2.1 spec Gemini drafted. It picks the structural wins from v2.1, drops the voice-optimization layer for now, and adds the few-shot retrieval scaffolding required to actually use the Golden Scenes Library and Bollywood Voice References.

## 0. What changes vs current code

**Replaced:**
- `stageBible` (gpt-4o) + `stageArc` (gpt-4o) merged into single `stageArchitect` call. One round-trip, one source of truth, no Bible-Arc drift.
- Scene output schema changes from `{narrator, dialogues[], img}` to `{scene_number, script}` where `script` is a single string using `*action*` markdown. The client parses this into UI nodes at render time.
- `saveGeneratedStory` now writes the row at end of Episode 1, then UPDATEs the same row as each subsequent episode completes (checkpoint saves).

**Added:**
- `story_state` memory vector — compact <150-token object recomputed after each episode, injected into the next.
- `secret` field in the architect blueprint, injected into every scene prompt.
- Character Voice Card — three sample dialogue lines for the protagonist, generated by the architect, threaded through every scene prompt.
- Few-shot example injection from `golden-scenes-v1.md` (and later `bollywood-voice-references-v1.md`).
- Anti-pattern example block in the scene prompt.
- Quality Validator pass on Episode 1 only (not all six episodes — cost discipline).
- Stream Episode 1 to the player — navigate user into reader as soon as ep1 returns; eps 2-6 generate in background.

**Deferred to v3.1+:**
- Story Mode (ROLEPLAY vs CINEMATIC perspective).
- Subgenre router (HORROR / MYSTERY / CRIME / CONSPIRACY / PSYCHOLOGICAL_SUSPENSE under THRILLER).
- Style anchor library + 80/20 exploit-explore router (needs retention telemetry first).
- Vector-search RAG over the dialogue library (hard-coded few-shot until volume justifies pgvector).
- Voice-match validator (voice optimization).
- Fine-tuning gpt-4o-mini on a distilled corpus (way too early).

## 1. Architecture

```
                    [User Prompt]
                          │
                          ▼
        ┌───────────────────────────────────┐
        │  Stage 1: The Architect           │ ◄── gpt-4o, single call
        │  → Bible + Story Rules            │     Returns blueprint with all 6 episodes
        │  → Secret, Character Voice Card   │     pre-planned (titles, scene objectives,
        │  → All 6 episode skeletons        │     cliffhangers, choices).
        └─────────────────┬─────────────────┘
                          │
                          ▼
        ┌───────────────────────────────────┐
        │  Stage 2: Episode 1 Scenes        │ ◄── gpt-4o-mini, single call (3 scenes)
        │  → Few-shot injection             │     Receives Golden Scene examples +
        │  → No prior state needed          │     character voice card.
        └─────────────────┬─────────────────┘
                          │
                          ▼
        ┌───────────────────────────────────┐
        │  Stage 3: Validator (ep1 only)    │ ◄── gpt-4o-mini, surgical rewriter
        │  → If fail: revise faulty scene   │     Only validates ep1 — make-or-break.
        └─────────────────┬─────────────────┘
                          │ 
            ┌─────────────┴─────────────┐
            ▼ (Instant)                 ▼ (Background)
   ┌─────────────────────┐    ┌───────────────────────────────────┐
   │ DB Checkpoint Save  │    │ Stage 4: Compute story_state v1   │ ◄── gpt-4o-mini
   │ Navigate to Reader  │    └─────────────────┬─────────────────┘
   └─────────────────────┘                      │
                                                ▼
                              ┌───────────────────────────────────┐
                              │ Stage 5: Episodes 2-6 (sequential)│ ◄── gpt-4o-mini
                              │  → Each ep both branches A+B      │     Each episode updates
                              │  → After each: DB checkpoint UPDATE│     story_state for next.
                              │  → After each: recompute story_state│
                              └───────────────────────────────────┘
```

**Cost vs current:** Architect single-call replaces two calls (Bible + Arc) — net neutral. Story-state recomputation adds ~5 small gpt-4o-mini calls (one per ep). Validator adds 1 call (ep1 only). Net cost: roughly +20-30% per generation. Worth it for the quality + UX gain.

**Latency to first scene:** Architect (~10-15s) + Ep1 scenes (~20-30s) + validator (~5-10s) = **~35-55 seconds to first playable scene**, vs ~3-5 minutes currently. This is the single largest UX move.

## 2. Schemas

### 2.1 Architect Blueprint

```json
{
  "genre": "ROMANCE" | "THRILLER" | "MYTHOLOGY",
  "title": "string (2-4 words, conversational Hinglish or Hindi)",
  "city": "string (Indian city)",
  "secret": "string (one sentence — hidden twist driving subtext)",
  "logline": "string (one sentence — protagonist, disruption, stakes)",
  "story_rules": [
    "string (permanent fact 1 — protagonist demographic, location, status)",
    "string (permanent fact 2 — plot-anchor that cannot be contradicted)",
    "string (permanent fact 3 — local/cultural constraint)"
  ],
  "protagonist": {
    "name": "string (first name)",
    "speech_tic": "string (their conversational verbal habit)",
    "voice_card": [
      "string (sample dialogue 1 — characteristic phrasing)",
      "string (sample dialogue 2 — different emotional register)",
      "string (sample dialogue 3 — under stress)"
    ]
  },
  "characters": [
    {
      "name": "string",
      "role": "string (relationship to protagonist + function)"
    }
  ],
  "episodes": [
    {
      "episode_number": 1,
      "title": "string",
      "scene_objectives": [
        "string (Scene 1 — mid-action entry point)",
        "string (Scene 2 — complication or escalation)",
        "string (Scene 3 — revelation that recontextualizes)"
      ],
      "target_cliffhanger": "string (exact sentence Scene 3 must end on)",
      "choice_question": "string (Hinglish dilemma)",
      "choice_a": { "label": "string (3-5 words)", "subtext": "string (hidden cost)" },
      "choice_b": { "label": "string (3-5 words)", "subtext": "string (hidden cost)" }
    }
    // ... eps 2-5 same shape
    // ep 6 same shape but omits choice_question, choice_a, choice_b
  ]
}
```

**Key additions vs current Bible schema:** `secret`, `protagonist.voice_card`, all 6 episode skeletons pre-planned (currently only ep arcs are planned in Stage 2). Removed: `cover_prompt` (kept for cover generation pipeline separately).

### 2.2 Story State Memory Vector

Recomputed at the end of each episode using a small gpt-4o-mini call. Injected into the next episode's scene-generation prompt.

```json
{
  "story_state": {
    "relationships": [
      { "pair": "string (e.g. 'Protagonist-Sironi')", "state": "string (current relational tension)" }
    ],
    "active_mysteries": [
      "string (unresolved question or revealed clue not yet acted on)"
    ],
    "emotional_state": "string (protagonist's current dominant feeling)",
    "objects": [
      "string (physical items introduced and still relevant)"
    ],
    "character_goals": [
      "string (what each named character is currently chasing)"
    ]
  }
}
```

**Token budget:** Compact JSON, target <150 tokens. If it grows beyond that, the recomputation prompt is failing — fix the prompt, not the cap.

### 2.3 Scene Output

```json
{
  "scenes": [
    {
      "scene_number": 1,
      "script": "*Action grounding the scene with one concrete sensory detail.* Character dialogue with no attribution tag. *Quick visual or sensory shift, half-sentence.* Next dialogue line, fragmented if appropriate."
    },
    { "scene_number": 2, "script": "..." },
    {
      "scene_number": 3,
      "script": "... *Final beat that lands the target cliffhanger sentence exactly.*"
    }
  ]
}
```

**The single-string `script` field is the big format change.** It lets the model interleave action and dialogue naturally — current `{narrator, dialogues[]}` forces "all narration first, then all dialogue" which reads stiff. Client-side parsing (Section 6) splits this into UI nodes.

## 3. Stage Prompts

### 3.1 The Architect (Stage 1)

- **Model:** `gpt-4o`
- **Response mode:** `response_format: { type: "json_object" }`

**System prompt:**

```
You are the lead story architect for Katha, an Indian interactive fiction app. You take a brief user premise and structure a complete 6-episode branching story blueprint.

GENRE FRAMEWORK:
- ROMANCE: Modern Indian setting. Class, family, or generational tension is the dominant conflict mechanism. The romance is obstructed by social structure, not by personality.
- THRILLER: Paranoia, mystery, or high-stakes survival. The protagonist starts ordinary; the world they wake into is not.
- MYTHOLOGY: A modern character is disrupted by an ancient or cosmic force they did not believe in. The supernatural arrives through physical wrongness, never through music or vocabulary.

CORE PRINCIPLES:
1. Every episode must end on a destination cliffhanger sentence Scene 3 will land on word-for-word.
2. The `secret` field is the central hidden truth that drives subtext across the entire story. Every scene operates around this secret even when it is not named.
3. The protagonist's `voice_card` (three sample dialogue lines) defines how this specific character speaks. These must be in the protagonist's natural register, demonstrating their verbal habit and one emotional range.
4. Story rules are permanent and cannot be contradicted by any later episode.
5. The 6 episodes must escalate. Episode 1 establishes; Episodes 2-5 complicate and branch; Episode 6 resolves.

OUTPUT: A single valid JSON object matching the schema. No markdown fences. Start directly with { and end with }.
```

**User prompt:**

```
User premise: "<USER_PROMPT>"

Build the complete blueprint. Generate skeletons for all 6 episodes — titles, scene objectives, target cliffhangers, and (for eps 1-5) the choice_question + choice_a + choice_b dilemma. Episode 6 omits the choice fields.

Schema:
<INLINE_SCHEMA_FROM_SECTION_2.1>
```

### 3.2 The Stateless Screenwriter (Stage 2)

- **Model:** `gpt-4o-mini`
- **Response mode:** `response_format: { type: "json_object" }`

**System prompt:**

```
You write one episode of three scenes for an Indian interactive fiction app. You receive the global blueprint and the current story state. You produce ONLY the three scenes for the requested episode.

OUTPUT FORMAT (CRITICAL):
- Each scene is a single string in the "script" field. No nested arrays.
- Wrap action / setting / internal state / physical movement in *asterisks*: *like this*.
- Character dialogue goes outside asterisks. NEVER use quotation marks. NEVER prepend dialogue with attribution ("Rahul said:", "Meera:", etc).
- Action and dialogue should INTERLEAVE within a single script string, not be batched (all action, then all dialogue).

LANGUAGE RULES:
- Hinglish: Roman-script Hindi-English code-switching the way urban Indian 18-30 year olds actually speak. The code-switch happens AT the emotionally loaded word, not at random.
- Concrete object similes over adjective declarations. "She was like a glass placed too close to a table edge" > "She was scared."
- Repetition with one altered element does emotional work. ("Bahut acha. Bahut acha.")
- The shortest sentence in a scene should be the heaviest. Land scenes on short final sentences.
- One Sanskrit/Urdu loanword per scene maximum. The supernatural is more frightening when it is grammatical, not ornamental.
- Direct address by name, title, or relation ("beta," "yaar," "sir," "bhaiya") is the load-bearing texture of Indian dialogue. Use it.

CRAFT RULES:
- Open scenes mid-action. No backstory exposition.
- One concrete sensory detail per beat — smell, sound, texture, temperature. Generic ("the room felt cold") is forbidden; specific ("the AC was set to 18 and her arms had goosebumps under her dupatta") is required.
- Show emotion through action, never through statement. "Meera reaches for her phone three times and puts it back" > "Meera was scared."
- Scene 3 MUST end with the exact target_cliffhanger sentence from the blueprint, word for word.
- Branch divergence: if a choice trajectory is provided, its consequence must be visible in Scene 1.

PIPELINE CONSTRAINTS:
- Story rules: <STORY_RULES_ARRAY> — these are permanent facts. Do not contradict.
- The Secret: "<SECRET>" — this drives subtext. Characters operate around it even without naming it.
- Memory state: <STORY_STATE_OBJECT> — relationships, mysteries, emotional state, objects. Maintain continuity.
- Banned phrases: <BANNED_LINES_CACHE> — do not reuse or paraphrase these.
- Previous final sentence: "<PREV_LAST_SENTENCE>" — Scene 1 must transition smoothly from this.
- Choice consequence: "<CHOICE_LABEL>" — the protagonist reached this episode by making this choice. Its cost must be visible in Scene 1.

PROTAGONIST VOICE CARD:
The protagonist speaks like this:
- <VOICE_CARD_LINE_1>
- <VOICE_CARD_LINE_2>
- <VOICE_CARD_LINE_3>
Their speech tic: "<SPEECH_TIC>" — use naturally, not in every line.

REFERENCE SCENES (match cadence, sensory specificity, and code-switching pattern — DO NOT copy content):

<INJECT 2 GOLDEN SCENES MATCHING (genre, scene_position) FROM golden-scenes-v1.md>

ANTI-PATTERN (do NOT write like this):

<INJECT 1 ANTI-PATTERN EXAMPLE — bad version of a scene with: generic sensory details, attribution tags, adjective-declaration emotions, no code-switching at load-bearing words>

OUTPUT: Single valid JSON object, no markdown fences.
```

**User prompt:**

```
Write Episode <N> of "<TITLE>" (Genre: <GENRE>).

Scene objectives:
1. <SCENE_OBJECTIVE_1>
2. <SCENE_OBJECTIVE_2>
3. <SCENE_OBJECTIVE_3>

Scene 3 must land this exact sentence at the end: "<TARGET_CLIFFHANGER>"

Output:
{
  "scenes": [
    { "scene_number": 1, "script": "..." },
    { "scene_number": 2, "script": "..." },
    { "scene_number": 3, "script": "... *ending on the target cliffhanger sentence*" }
  ]
}
```

### 3.3 Validator (Stage 3, Episode 1 only)

- **Model:** `gpt-4o-mini`
- **Response mode:** `response_format: { type: "json_object" }`
- **Run on:** Episode 1 only. Episodes 2-6 skip validation — cost discipline, ep1 is the make-or-break.

**System prompt:**

```
You audit one episode for structural quality before it ships to the player.

CHECKS:
1. Does Scene 3 end on the exact target_cliffhanger sentence?
2. Does each scene open mid-action, no exposition?
3. Is there at least one concrete sensory detail per scene? (Not generic — specific.)
4. Are emotions shown through action, not stated?
5. Does dialogue avoid attribution tags ("Rahul said:")?
6. Does the script use *action* / dialogue interleaving rather than batched narration-then-dialogue?
7. Does code-switching happen at the emotionally loaded word, not randomly?
8. Are any story rules contradicted?
9. Does any phrase echo the banned-lines cache?

If everything passes, set pass: true.
If any check fails, set pass: false, identify the single scene that failed (target_node), and produce a corrected `revised_script` for that scene only. Do not regenerate the whole episode.

Output: raw JSON object, no markdown fences.

{
  "pass": true | false,
  "issues": ["specific check that failed"],
  "target_node": 1 | 2 | 3 | null,
  "revised_script": "..." | null
}
```

### 3.4 Story State Recomputer (Stage 4)

- **Model:** `gpt-4o-mini`
- **Cheap call, runs after each episode.**

**System prompt:**

```
You update a compact story-state memory after each episode of an interactive fiction app. The memory is passed to the next episode's writer to prevent continuity drift.

You receive: the current story_state and the just-completed episode's scripts. You return: the updated story_state.

Token budget: <150 tokens total. Be ruthlessly compact.

Update rules:
- relationships: only update if a relationship's state has shifted. Don't list every pair.
- active_mysteries: add new unresolved hooks; remove ones that were resolved this episode.
- emotional_state: a single phrase describing the protagonist's current dominant feeling.
- objects: only items that will plausibly matter in a future scene.
- character_goals: what each named character is currently chasing. Update only if it changed.

Output: raw JSON, no markdown fences.
```

## 4. Few-shot injection strategy

### 4.1 v3 — Hard-coded retrieval (ship first)

In `golden-scenes-v1.md`, scenes are tagged with `(genre, scene_position)`. At Stage 2 prompt construction:

```js
function selectGoldenExamples(genre, episode_number) {
  // Episode 1 → OPENER + MIDPOINT
  // Episode 2-5 → MIDPOINT + CLIFFHANGER
  // Episode 6 → CLIFFHANGER + MIDPOINT
  const positionMap = {
    1: ["OPENER", "MIDPOINT"],
    6: ["CLIFFHANGER", "MIDPOINT"]
  };
  const positions = positionMap[episode_number] || ["MIDPOINT", "CLIFFHANGER"];
  return positions.map(pos => GOLDEN_SCENES.find(s => s.genre === genre && s.scene_position === pos));
}
```

Embed `GOLDEN_SCENES` as a JS constant in `index.html` (or a small JSON file fetched once at app load). ~9 scenes total — tiny payload.

### 4.2 v3.1 — pgvector retrieval (later)

Once the Golden Scenes Library grows past ~30 scenes and the Bollywood Voice References past ~100 entries, switch to vector retrieval:

1. Embed each entry using `text-embedding-3-small`.
2. Store vectors in Supabase with `pgvector`.
3. At Stage 2, embed the current scene context (genre + scene_objective + emotional_beat from the blueprint) and retrieve top-3 nearest neighbours.
4. Inject those as the few-shot block.

Don't ship this until you have the volume. Hard-coded few-shot is correct for v3.

## 5. Checkpoint save logic

Replace the current end-of-pipeline `_saveStoryToDb` with progressive UPDATEs.

```js
async function runPipelineV3(userPrompt) {
  // Stage 1: Architect
  const blueprint = await stageArchitect(userPrompt);

  // Stage 2: Episode 1 scenes
  const ep1Examples = selectGoldenExamples(blueprint.genre, 1);
  const ep1Scenes = await stageScenes({
    blueprint,
    episodeNumber: 1,
    story_state: null,
    prev_last_sentence: null,
    choice_label: null,
    banned_lines: [],
    examples: ep1Examples
  });

  // Stage 3: Validator
  const validation = await stageValidate(ep1Scenes, blueprint);
  if (!validation.pass && validation.revised_script) {
    ep1Scenes.scenes[validation.target_node - 1].script = validation.revised_script;
  }

  // First checkpoint save — story now exists in DB with ep1 only
  const partial = assembleStory(blueprint, [ep1Scenes], null);
  const storyId = await _saveStoryToDbInitial(partial, blueprint);

  // Navigate to reader IMMEDIATELY — user starts playing ep1
  CURRENT_STORY = partial;
  CURRENT_STORY_ID = storyId;
  setGenEta('Episode 1 ready — opening reader');
  startStory();

  // Background: generate eps 2-6, checkpoint after each
  generateRemainingEpisodesInBackground(blueprint, ep1Scenes, storyId);
}

async function generateRemainingEpisodesInBackground(blueprint, ep1Scenes, storyId) {
  let story_state = await stageRecomputeState(null, ep1Scenes, blueprint);
  let banned_lines = extractBannedLines(ep1Scenes);
  let prev_last_sentence = extractLastSentence(ep1Scenes);
  const allEpisodes = [ep1Scenes];

  for (let n = 2; n <= 6; n++) {
    const examples = selectGoldenExamples(blueprint.genre, n);
    const epBlueprint = blueprint.episodes[n - 1];

    // Both branches A + B in parallel (matching current code's structure)
    const [branchA, branchB] = await Promise.all([
      stageScenes({ blueprint, episodeNumber: n, story_state, prev_last_sentence, choice_label: prevChoiceA, banned_lines, examples }),
      stageScenes({ blueprint, episodeNumber: n, story_state, prev_last_sentence, choice_label: prevChoiceB, banned_lines, examples })
    ]);

    allEpisodes.push({ A: branchA, B: branchB });
    banned_lines.push(...extractBannedLines(branchA), ...extractBannedLines(branchB));
    if (banned_lines.length > 72) banned_lines.splice(0, banned_lines.length - 72);

    // Checkpoint UPDATE — story row grows as eps complete
    const partial = assembleStory(blueprint, allEpisodes, null);
    await _updateStoryInDb(storyId, partial);

    // Recompute state for next ep
    story_state = await stageRecomputeState(story_state, branchA, blueprint);
    prev_last_sentence = extractLastSentence(branchA); // pick A's tail by default
  }

  // Final cover image — fire after all text is done
  const coverImg = await oaiImage(buildCoverPrompt(blueprint));
  await _updateStoryInDb(storyId, assembleStory(blueprint, allEpisodes, coverImg));
}
```

**Why checkpoint after every episode rather than batch:**
- If the pipeline crashes mid-way (network drop, browser tab killed, token expiry), the user keeps every validated episode.
- Solves the root data-loss problem at a structural level — the `pendingDbSave` patch shipped recently is now redundant once this lands.
- Same `stories.id` row throughout — no schema change needed.

## 6. Client-side script parser

Replace the current scene-rendering code that expects `{narrator, dialogues}` with a parser for the new `script` string.

```js
function parseScriptStringToUiNodes(scriptString) {
  const nodes = [];
  // Match *action* blocks OR plain dialogue between them
  const pattern = /(\*[^*]+\*)|([^*]+)/g;
  let match;
  while ((match = pattern.exec(scriptString)) !== null) {
    if (match[1]) {
      const action = match[1].replace(/\*/g, '').trim();
      if (action) nodes.push({ type: 'ACTION_PROSE', text: action });
    } else if (match[2]) {
      const dialogue = match[2].trim();
      if (dialogue) nodes.push({ type: 'CHARACTER_DIALOGUE', text: dialogue });
    }
  }
  return nodes;
}
```

**Render rules:**
- `ACTION_PROSE` nodes render as italicized prose, smaller font, muted color.
- `CHARACTER_DIALOGUE` nodes render as primary text, larger, full color.
- Sequential nodes of the same type get a tighter line-height than transitions.

**Back-compat:** Add a `version` field on `story_data` in the DB. v3-generated stories have `version: "v3"`. Old stories (no version field) render with the old `{narrator, dialogues}` renderer. Lazy migration only — never bulk-rewrite old stories.

## 7. Migration plan from current code

The current pipeline lives in `index.html` between roughly line 2179 (`stageBible`) and line 2565 (end of `runPipeline`). Migration is single-file, no schema changes.

**Step 1 — keep the old code working alongside the new.** Build v3 as `runPipelineV3` next to `runPipeline`. Wire `startGenerating` to a feature flag (`USE_V3_ENGINE = true/false`). Ship dark. Test internally.

**Step 2 — schema additions.** Add `secret`, `voice_card`, full episode skeletons to the architect output. Update `assembleStory` to accept the new shape. Add `version` field to `story_data`.

**Step 3 — parser swap.** Build `parseScriptStringToUiNodes`. Update the reader render path to use it for `version: "v3"` stories. Keep the old path for stories without a version field.

**Step 4 — checkpoint save.** Replace single end-of-pipeline save with the initial save after ep1 + UPDATE after each subsequent episode. Once this lands and works, the `pendingDbSave` flag from the recent fix becomes redundant — remove it.

**Step 5 — golden scenes wire-up.** Embed `GOLDEN_SCENES` array in `index.html` (from `golden-scenes-v1.md`). Add `selectGoldenExamples` retrieval. Inject into Stage 2 prompt.

**Step 6 — flip the flag.** Set `USE_V3_ENGINE = true` in prod. Monitor: generation success rate, ep1-to-ep2 retention, average time-to-first-scene, average payload size.

**Step 7 — keep the old code for two weeks**, then delete once v3 has been stable. Old saved stories continue to render through the back-compat path.

## 8. What we are NOT doing in v3

For clarity, explicit list of what stays out:

- **Story Mode (ROLEPLAY vs CINEMATIC)** — voice optimization. Both perspectives can be added once v3 ships and we have data on which one retains better.
- **Subgenre under THRILLER** — useful eventually but adds a routing layer the engine doesn't need to ship.
- **Style Anchor Library + 80/20 router** — requires retention telemetry data that doesn't exist yet. Premature.
- **Voice-match validator** — adds a per-scene call. Skip until we know if structural validator (ep1 only) is even necessary.
- **Fine-tuning gpt-4o-mini** — way too early. Run on few-shot for at least 3 months before considering.
- **Vector retrieval (pgvector)** — overkill for ~9 hard-coded examples. Add later when library grows past ~30 entries.
- **Image generation for scene-level art** — current pipeline only generates a cover. v3 keeps it that way.

## 9. Open questions for review

These are decisions I made tentatively. Flag any to revisit:

1. **Validator on ep1 only vs all 6** — I chose ep1 only for cost discipline. The counter-argument: continuity drift compounds, and a bad ep4 could break the story. Test both and measure.
2. **`*action*` markdown vs structured `{narrator, dialogues[]}`** — this is the riskiest format change. The new format gives the model real freedom to interleave; the old format is safer to render. I recommend `*action*` because the freedom matters more for quality.
3. **Story-state recomputation as a separate LLM call vs extracting heuristically** — I chose LLM-extraction. A heuristic version (regex over episode scripts) would be cheaper but more brittle. The LLM call is ~$0.0003 per episode — keep it.
4. **`secret` exposed to player anywhere** — the architect generates a secret that drives subtext. It is never directly shown to the player. Confirm this is the intent (rather than e.g. revealing it as a "twist" in ep6).
5. **Single A/B branch persistence vs full tree** — current code generates both A and B branches for eps 2-6 and stores both. v3 keeps this. Player choice determines which they read; the other branch is dormant in the DB. Confirm: keep this structure?

## 11. Success metrics

After shipping v3, measure for at least 2 weeks before deciding what to do next:

- **Time-to-first-scene** — target: under 60 seconds (vs current ~3-5 min)
- **Generation success rate** — target: >95% (vs current — unknown, instrument first)
- **Episode-1-to-Episode-2 retention** — the make-or-break metric. Anything below 50% means ep1 quality is still failing. Anything above 70% means structure is working and we can invest in voice.
- **Story payload size** — target: under 200KB after stripping base64. If creeping toward 500KB, examine why.
- **Validator pass rate on ep1** — target: >80% pass first try. Below this means the scene prompt is too weak. Above 95% means the validator is too lenient.

The retention number is the only one that matters for the product call. Everything else is instrumentation.
